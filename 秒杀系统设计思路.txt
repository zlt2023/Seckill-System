================================================================================
                           秒杀系统 - 完整设计方案
================================================================================

【技术栈】
  前端：Vue 3 + Vite + Element Plus + Pinia + Axios
  后端：Java 17 + Spring Boot 3 + MyBatis-Plus
  缓存：Redis 7 (Lua 脚本)
  数据库：MySQL 8
  消息队列：RabbitMQ
  认证：JWT (无状态)
  构建：Maven

================================================================================
二、系统架构 - 流量漏斗模型
================================================================================

  核心思想：层层递减，绝不让高并发流量直接打到 MySQL

  用户请求 (100%)
      │
      ▼
  ┌─────────────────────────────────┐
  │ 第1层: 前端防护                  │ → 按钮防抖(点击后置灰3秒)
  │   按钮置灰 + 倒计时校验          │   倒计时未归零不可点击
  └─────────────────────────────────┘
      │
      ▼
  ┌─────────────────────────────────┐
  │ 第2层: Nginx 限流               │ → 拦截 ~40% 恶意/超频请求
  │   limit_req + IP黑名单          │   同一IP每秒最多N次请求
  └─────────────────────────────────┘
      │
      ▼
  ┌─────────────────────────────────┐
  │ 第3层: 接口安全校验              │ → 拦截 ~30% 脚本/Bot请求
  │   JWT认证 + 动态路径Token校验    │   路径Token 60秒过期
  └─────────────────────────────────┘
      │
      ▼
  ┌─────────────────────────────────┐
  │ 第4层: JVM 内存标记              │ → 已售罄商品直接返回
  │   localOverMap 本地缓存          │   不访问Redis，最快失败 (L1缓存)
  └─────────────────────────────────┘
      │
      ▼
  ┌─────────────────────────────────┐
  │ 第5层: Redis Lua 原子扣减        │ → 整合校验：行政状态 + 时间 + 库存
  │   Hash 存储 + Set 判重           │   一次网络往返完成所有准入校验
  └─────────────────────────────────┘
      │
      ▼  (仅 ~1% 请求到达此处)
  ┌─────────────────────────────────┐
  │ 第6层: RabbitMQ 异步入队         │ → 削峰填谷，保护数据库
  │   消费者扣减MySQL库存+生成订单   │   平稳消费，最终一致
  └─────────────────────────────────┘

================================================================================
四、Redis 缓存设计
================================================================================

【Key 命名规范】

  Key 模式                                    类型     说明                 过期时间
  ─────────────────────────────────────────────────────────────────────────────────
  seckill:info:{seckillGoodsId}               Hash     核心元数据聚合        活动结束后+1h
                                                      (startTime/endTime/price/stock/status)
  seckill:bought:{seckillGoodsId}             Set      已购买用户ID集合      活动结束后+1h
  seckill:path:{userId}:{seckillGoodsId}      String   动态秒杀路径Token     60秒
  seckill:result:{userId}:{seckillGoodsId}    String   秒杀结果(0排队/1成功/2失败) 30分钟
  
【Lua 脚本 - 原子扣减库存】

  -- KEYS[1] = seckill:info:{id}        聚合信息Hash (源头数据)
  -- KEYS[2] = seckill:bought:{id}      已购买集合Key
  -- ARGV[1] = userId
  -- ARGV[2] = nowTime (当前服务器毫秒时间)

  步骤1: 检查行政状态 → HGET KEYS[1] "status" 
         status != 1 → return -3 (活动已手动下架或暂停)

  步骤2: 校验时间视窗 → HGETS KEYS[1] "startTime" "endTime"
         nowTime < startTime → return -4 (秒杀未开始)
         nowTime >= endTime → return -4 (秒杀已结束，含边界时间点)

  步骤3: 检查重复购买 → SISMEMBER KEYS[2] ARGV[1]
         已存在 → return -2

  步骤4: 校验并原子扣减库存 → HGET KEYS[1] "stock"
         库存 <= 0 → return -1
         库存 > 0  → HINCRBY KEYS[1] "stock" -1, SADD KEYS[2] ARGV[1], return 1

  返回值含义:
     1  → 预占成功，进入MQ异步订单流
    -1  → 库存不足/售罄
    -2  → 重复购买
    -3  → 活动非上架状态
    -4  → 非秒杀时段

  [!] Lua脚本在Redis中原子执行，天然解决高并发下的超卖与重入问题。

【缓存预热机制】
  时机: Spring Boot 启动 (ApplicationRunner) 或 管理端手动 Reload
  逻辑: 1. 执行 Redis 深度清理 (Deep Clean)，清空所有 `seckill:*` 历史冗余 Key。
        2. 扫描数据库中 `status=1` 且 `endTime > now` 的活跃活动。
        3. 批量将活动元数据封装进 `seckill:info:{id}` Hash 结构中。
        4. 设置 Key 生存周期为 (活动结束时间 + 1小时缓冲)，实现自动内存释放。


================================================================================
五、RabbitMQ 消息队列设计
================================================================================

【队列拓扑】

  秒杀服务(Producer)
      │
      │ 发送秒杀消息
      ▼
  seckill.exchange (Direct交换机)
      │
      │ routing-key: seckill.order
      ▼
  seckill.order.queue (秒杀订单队列)
      │
      │ 消费消息
      ▼
  订单消费者 (SeckillMessageConsumer)
      │
      │ 消费失败/超过重试次数
      ▼
  seckill.dlx.exchange (死信交换机)
      │
      ▼
  seckill.dlq.queue (死信队列) → 人工监控/告警

【消息体】
  {
    "userId": 10001,
    "seckillGoodsId": 5,
    "seckillPrice": 99.00,
    "timestamp": 1711929600000,
    "requestId": "uuid-xxxx"     ← 幂等性标识
  }

【消费者处理流程】

  接收MQ消息
      │
      ▼
  获取 Redis 分布式锁 (setnx防高并发消息重放)
      │
      ▼
  幂等性检查: 该用户+该商品是否已有[待支付/已支付]订单？
      │
  ┌───┴───┐
  │已存在  │ → 跳过处理，ACK消息
  │       │
  │不存在  │ → 开启数据库事务
  └───┬───┘
      │
      ▼
  MySQL扣减库存 (最终行政防御):
  UPDATE t_seckill_goods SET available_stock = available_stock - 1
  WHERE id = ? AND available_stock > 0 AND status = 1
      │
  ┌───┴───┐
  │成功    │ → 创建订单(INSERT t_seckill_order)
  │(rows>0)│   → Redis设置 result = 1 (成功)
  │       │   → 发送延迟消息(订单超时取消，15分钟)
  │       │   → 提交事务，ACK消息
  │       │
  │失败    │ → Redis回滚: INCR库存 + SREM购买标记
  │(rows=0)│   → Redis设置 result = 2 (失败)
  └───────┘   → ACK消息

【可靠性保障】
  · 开启 Publisher Confirm (生产者确认，防消息丢失)
  · 消费端手动 ACK (处理完才确认)
  · 失败重试最多3次，超限进入死信队列
  · 唯一索引 uk_order_no 订单编号唯一 (数据库兜底幂等性)
  · Redis 分布式锁防短时并发消费 (10秒过期，仅保护幂等性检查)

六、秒杀核心流程 (详细版)
================================================================================

┌──────────────────────────────────────────────────────────────────────────────┐
│                        完 整 秒 杀 流 程                                     │
├──────────────────────────────────────────────────────────────────────────────┤
│                                                                              │
│  ==================== 阶段1: 获取动态路径 ====================               │
│                                                                              │
│  用户点击[抢购]按钮                                                           │
│      │                                                                       │
│      ▼                                                                       │
│  前端 → GET /api/seckill/path/{seckillGoodsId}                              │
│      │                                                                       │
│      ▼                                                                       │
│  后端生成随机Token(UUID) → 存入Redis(60秒TTL) → 返回Token                    │
│                                                                              │
│  ==================== 阶段2: 执行秒杀 ====================                  │
│                                                                              │
│  前端 → POST /api/seckill/{token}/execute?seckillGoodsId=5                  │
│      │                                                                       │
│      ▼                                                                       │
│  ① 验证动态路径Token (Redis中是否匹配)                                       │
│      │ 无效 → 返回"非法请求"                                                 │
│      │ 有效 ↓                                                                │
│      ▼                                                                       │
│  ② JVM内存标记检查 (localOverMap)                                            │
│      │ 已售罄 → 直接返回"已售罄"                                              │
│      │ 未售罄 ↓                                                               │
│      ▼                                                                       │
│  ③ 执行Redis Lua脚本 (原子操作)                                              │
│      │                                                                       │
│      ├─ return -1 → 已售罄，更新JVM本地标记，返回"已售罄"                     │
│      ├─ return -2 → 返回"请勿重复购买"                                        │
│      └─ return  1 ↓                                                          │
│      ▼                                                                       │
│  ④ 发送MQ消息到 seckill.order.queue                                          │
│  ⑤ Redis设置 result = 0 (排队中)                                             │
│  ⑥ 返回前端 "排队中，请等待结果"                                              │
│                                                                              │
│  ==================== 阶段3: 异步下单 ====================                   │
│                                                                              │
│  MQ消费者接收消息                                                             │
│      │                                                                       │
│      ▼                                                                       │
│  幂等性检查 → 数据库事务{扣减MySQL库存 + 创建订单}                             │
│      │                                                                       │
│      ├─ 成功  → Redis result = 1, 发送延迟消息(15分钟超时取消)                │
│      └─ 失败  → Redis回滚库存, Redis result = 2                              │
│                                                                              │
│  ==================== 阶段4: 轮询结果 ====================                   │
│                                                                              │
│  前端每2秒轮询: GET /api/seckill/result/{seckillGoodsId}                     │
│      │                                                                       │
│      ├─ result = 0  → 继续轮询 (最多15次/30秒)                                │
│      ├─ result = 1  → 抢购成功！显示订单号，跳转支付                           │
│      └─ result = 2  → 抢购失败，提示"库存不足，请下次再试"                     │
│                                                                              │
│  ==================== 阶段5: 订单超时取消 ====================               │
│                                                                              │
│  用户15分钟内未支付                                                           │
│      │                                                                       │
│      ▼                                                                       │
│  延迟队列消息到期(TTL+DLX) → 超时消费者检查订单状态                           │
│      │                                                                       │
│      ├─ 已支付 → 跳过                                                        │
│      └─ 待支付 → UPDATE status=3(超时)                                       │
│                → MySQL available_stock + 1                                   │
│                → Redis INCR库存 + SREM购买标记                               │
│                                                                              │
└──────────────────────────────────────────────────────────────────────────────┘

七、安全防护设计 (5层防御体系)
================================================================================

  第1层【前端防护】
    · 抢购按钮点击后置灰3秒(防抖)
    · 倒计时未归零时按钮禁用
    · 前端请求频率限制

  第2层【Nginx防护】
    · limit_req 限流 (每秒N次/IP)
    · IP黑名单过滤

  第3层【接口安全】
    · JWT Token 身份认证
    · 动态秒杀路径 pathToken (60秒有效)
    · 接口级限流 (Redis计数器 + 自定义注解@RateLimit)

  第4层【业务防护】
    · JVM内存标记 (售罄商品本地缓存)
    · Redis Lua 重复购买检查 (SISMEMBER)
    · Redis Lua 库存原子扣减

  第5层【数据库兜底与并发安全】
    · Redis 分布式防重锁兜底消息高并发幂等性 (允许合法重买)
    · 秒杀下单扣库存: WHERE available_stock > 0 乐观锁防超卖
    · 订单状态流转: UPDATE status = ? WHERE status = 0 原子更新防竞态(TOCTOU)

【动态路径设计(接口隐藏)】
  目的: 防止用户提前知道秒杀接口URL，用脚本直接刷

  秒杀前 → 接口地址未知
      ↓
  用户点击抢购 → GET /api/seckill/path/{goodsId}
      ↓
  后端生成随机Token → 存入Redis(60秒过期)
      ↓
  前端拼接真正请求 → POST /api/seckill/{token}/execute
      ↓
  后端校验Token是否匹配Redis记录

【自定义限流注解】
  @AccessLimit(seconds = 5, maxCount = 5, needLogin = true)
  含义: 同一用户5秒内最多访问5次
  实现: AOP拦截 + Redis INCR + EXPIRE

【核心交互】

  (1) 倒计时组件
      · 页面加载时请求 GET /api/seckill/time 获取服务器时间
      · 计算 serverTimeDiff = 服务器时间 - 本地时间 - 网络延迟/2
      · setInterval 每秒更新倒计时显示
      · 倒计时归零后自动激活抢购按钮
      · 组件销毁时清除定时器(防内存泄漏)

  (2) 抢购流程
      用户点击[立即抢购] → 按钮置灰
        → 请求动态路径
        → 提交秒杀请求
        → 显示"排队中..."
        → 每2秒轮询结果(最多15次)
        → 成功: 显示订单号 + [前往支付]
        → 失败: 提示原因，恢复按钮

  (3) 结果轮询
      · 轮询接口: GET /api/seckill/result/{seckillGoodsId}
      · 间隔: 2秒
      · 最大次数: 15次(30秒超时)
      · result=0 继续轮询, result=1 成功, result=2 失败

十、数据一致性保障
================================================================================

【正常流程一致性】
  环节                  Redis状态               MySQL状态             结果
  ───────────────────────────────────────────────────────────────────────
  Lua扣减成功           库存-1, 用户加入Set     无变化                 -
  MQ消费成功            result=1(成功)          库存-1, 订单已创建     最终一致 ✓
  MQ消费失败(库存不足)  库存+1回滚, 移出Set     无变化                 回滚一致 ✓

【异常场景处理】
  场景                        处理方案
  ──────────────────────────────────────────────────────────────────
  Redis扣减后MQ发送失败       捕获异常，回滚Redis(INCR + SREM)
  MQ消费者处理超时            消息重投(最多3次)，幂等性检查兜底
  Redis宕机                   从MySQL重新加载缓存，触发预热
  MySQL宕机                   MQ消息保留，待恢复后重新消费
  Redis与MySQL库存不一致      定时对账任务每5分钟修复(以MySQL为准)

【定时对账任务】
  · 频率: 每天凌晨2点执行 (SeckillOrderTask.reconcileData)
  · 逻辑: 查询所有秒杀商品
          → 对比Redis库存 vs MySQL available_stock
          → 不一致时以MySQL为准修正Redis
          → 检查bought Set一致性（清理已取消/超时但仍在Set中的用户）
          → 销量对账（售出总量与有效订单数对比）
          → 记录告警日志

【秒杀状态与缓存维护】
  · 频率: 每10分钟执行 (SeckillOrderTask.scanTimeoutOrders)
  · 逻辑: 扫描超时未支付订单（创建时间在16分钟前的待支付订单）
          → 自动取消超时订单并回滚库存
          → 与MQ延迟消息形成双保险


================================================================================
十一、订单超时取消 (延迟队列)
================================================================================

【方案: RabbitMQ TTL + DLX (死信交换机)】

  订单创建成功
      │
      ▼
  发送延迟消息到 delay.queue (消息TTL=15分钟)
      │
      │ 15分钟后消息过期
      ▼
  转发到死信交换机 → cancel.queue
      │
      ▼
  OrderTimeoutConsumer 消费超时消息
      │
      ▼
  查询订单状态
      │
  ┌───┴───┐
  │已支付  │ → 跳过，无需处理
  │       │
  │待支付  │ → 原子更新 UPDATE status = 3 WHERE status = 0 (防并发支付冲突)
  │       │   UPDATE available_stock + 1 (MySQL回滚)
  │       │   Redis INCR库存 + SREM购买标记
  │       │   清除 JVM localOverMap 售罄标记 (允许恢复抢购)
  └───────┘
